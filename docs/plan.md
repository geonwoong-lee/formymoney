# Very Rich? 개발 계획

## 0. 목적과 확정 기술

이 문서는 `docs/spec.md`를 React 프론트엔드와 FastAPI 백엔드로 구현하는 순서를 정한다.

| 영역 | 확정 기술 | 역할 |
|---|---|---|
| 프론트엔드 | React + TypeScript | 입력, 화면 이동, 로컬 저장, 결과·오류 표시 |
| 백엔드 | FastAPI | 입력 검증, 기준 데이터 조회, 모든 핵심 금융 계산 |
| 운영 DB | Supabase PostgreSQL | 은행·상품·우대조건·출처·투자 기준 데이터 |
| 개발·테스트 DB | SQLite3 | 로컬 개발, API·계산 자동 테스트 |

계산은 비회원도 사용할 수 있다. 회원가입·로그인은 Supabase Auth를 사용하며, 비회원 답변과 납입액은 브라우저에만 저장한다.

사용자 화면과 문서에는 `Very Rich?`를 사용한다. 폴더명, 패키지명과 배포 주소처럼 물음표를 사용할 수 없는 곳에는 `very-rich`를 사용한다.

---

## 1. 개발 원칙

1. 화면보다 공식 데이터와 계산 정확성을 먼저 확보한다.
2. React는 금융 계산을 복제하지 않고 FastAPI 결과를 표시한다.
3. FastAPI 계산 코드는 Supabase와 SQLite3 중 어느 DB를 사용해도 같은 결과를 내야 한다.
4. 비회원 입력은 DB에 저장하지 않는다. 회원 개인 기록과 별도 동의한 익명 분석 데이터는 서로 분리한다.
5. SQLite3 테스트 통과만으로 운영 호환성을 단정하지 않고 Supabase 연결 검증을 별도로 한다.
6. 은행 비교를 먼저 완성하고 월별 납입, 투자 비교 순으로 확장한다.
7. 계산할 수 없는 조건은 임의 숫자로 만들지 않는다.

## 3. Phase 0 — 개발 기준 확정

### 목표

프로젝트 생성 전에 구조와 저장 원칙을 확정한다.

### 확정 사항

- 프로젝트 루트 아래 `frontend/`, `backend/`로 분리한다.
- 프론트엔드는 React + TypeScript를 사용한다.
- 백엔드는 FastAPI를 사용한다.
- 로컬·자동 테스트 DB는 SQLite3를 사용한다.
- 운영 DB는 Supabase PostgreSQL을 사용한다.
- 비회원 입력은 React의 브라우저 로컬 저장소에만 보관한다.
- FastAPI는 비회원 계산 요청을 영구 저장하지 않는다.
- 회원가입·로그인은 Supabase Auth를 사용하고 자체 비밀번호 DB는 만들지 않는다.
- `처음부터 다시 입력`으로 브라우저 입력을 초기화한다.

### 결정이 남은 내용

- 첫 지원 은행 범위
- 질문을 한 화면에 묶을지 단계별로 보여줄지
- 기존 거래 은행 입력 위치
- 나스닥100·채권의 정확한 비교 기준
- 투자 기간, 환율, 세금과 수수료 처리

투자 관련 결정은 Phase 6 전까지 미뤄도 된다.

### 권장 폴더 구조

```text

├─ frontend/
│  ├─ src/
│  │  ├─ pages/
│  │  ├─ components/

├─ backend/
│  ├─ app/
```

### 완료 조건

- 기술과 저장 원칙이 PRD·spec·plan에서 서로 일치함
- 사용자 입력과 기준 데이터의 저장 위치가 구분됨
- Phase 1을 시작하는 데 필요한 추가 계정이나 키가 없음

## 4. Phase 1 — React·FastAPI·SQLite3 기반 구축

### 목표

실제 기능 개발 전에 프론트엔드, 백엔드와 테스트 DB가 통신하는 최소 구조를 만든다.

### 1-1. 프론트엔드 생성

- React + TypeScript 프로젝트 생성
- 기본 라우팅 구성
- `/`, `/conditions`, `/banks`, `/banks/[id]`, `/cashflow`, `/alternatives`, `/about` 경로 준비
- 공통 레이아웃과 모바일 기준 폭 준비
- API 요청 모듈 준비
- 브라우저 로컬 저장 모듈 준비

### 1-2. 백엔드 생성

- FastAPI 프로젝트 생성
- API 버전 경로 구성
- 요청·응답 스키마 구조 준비
- 서비스, 계산기, 저장소 계층 분리
- 공통 오류 응답 형식 준비
- 허용된 프론트엔드 주소에서만 개발 요청을 받을 수 있게 설정

### 1-3. SQLite3 연결

- 로컬 개발용 SQLite3 연결 설정
- 기준 데이터용 초기 테이블 준비
- 테스트마다 독립 DB를 만들고 초기화할 수 있게 구성
- 운영 DB에 종속된 PostgreSQL 전용 기능은 아직 사용하지 않음

### 1-4. 최소 연결 확인

- FastAPI 상태 확인 API 준비
- React가 상태 확인 API를 호출해 정상 응답을 표시
- 백엔드가 SQLite3에 연결해 기준 데이터 한 건을 읽는지 확인
- 사용자 입력이 DB에 저장되지 않는지 확인

### 1-5. 테스트 기반

- 백엔드 단위 테스트
- FastAPI 요청·응답 테스트
- SQLite3 저장소 테스트
- React 기본 화면·입력 테스트
- 프론트엔드와 백엔드 실행 방법 문서화

### 산출물

- 실행 가능한 React 앱
- 실행 가능한 FastAPI 앱
- SQLite3 개발·테스트 설정
- 최소 API 통신
- 기본 테스트 명령
- 환경변수 예시 파일

### 완료 조건

- 프론트엔드와 백엔드를 각각 실행할 수 있음
- React에서 FastAPI 정상 응답을 확인할 수 있음
- 자동 테스트가 SQLite3로 실행됨
- 비밀값이 저장소에 포함되지 않음
- 금융 기능은 아직 임시 숫자로 구현하지 않음

## 5. Phase 2 — 공식 상품 데이터 구축

**완료(2026-10-29):** 청년미래적금 14개 취급기관의 상품과 우대조건 82개, 공식 출처를 구축하고 Supabase에 적재했다. 자동 테스트에서는 같은 모델을 SQLite3에 초기화한다.

### 목표

청년미래적금 계산에 필요한 공통 규칙과 은행별 공시를 DB 구조로 정리한다.

### 작업

1. 공통 상품 규칙 정리
   - 가입 기간과 납입 범위
   - 정부기여금과 세금 규칙
   - 전환 가입 관련 규칙
2. 첫 지원 은행 범위 확정
3. 은행별 정보 정리
   - 은행·상품명
   - 기본·최고금리
   - 우대조건과 가산금리
   - 조건 결합 방식
   - 공시 URL과 기준일
4. 사용자 질문, 계산 조건, 쉬운 설명을 분리
5. 자동 계산 불가능 조건을 `추가 확인 필요`로 구분
6. SQLite3 초기 데이터 작성
7. 공식 원문과 사람 검수

### DB 원칙

- Supabase와 SQLite3에서 사용할 핵심 필드명을 같게 유지한다.
- 사용자 답변이나 계산 결과 테이블은 만들지 않는다.
- 금액과 금리는 부동소수점 오차를 피할 수 있는 형식으로 다룬다.
- 모든 공시 데이터에 기준일과 출처를 둔다.

### 완료 조건

- 지원 은행 데이터가 빠짐없이 SQLite3에 들어 있음
- 모든 금리와 조건에 공식 근거가 있음
- 최고금리와 조건별 금리 합계가 검수됨
- 자동 계산 보류 조건이 분리됨

## 6. Phase 3 — 적금 계산 API 완성

**완료(2026-10-28):** 상품·질문 조회 API와 고정 월 납입 계산 API를 구현했다. `모름`과 추가 증빙 조건은 금리에서 제외하며 17개 백엔드 테스트를 통과했다.

### 목표

FastAPI가 사용자 입력과 SQLite3 기준 데이터를 이용해 적금 결과와 근거를 반환하게 한다.

### 작업

1. 기본 계획 요청 검증
2. 우대조건 상태 계산
   - 반영됨
   - 반영되지 않음
   - 추가 확인 필요
3. 예상금리 계산
4. 월 기본 납입 기준 이자 계산
5. 정부기여금 계산
6. 예상 만기 수령액 계산
7. 은행별 결과 정렬용 값 반환
8. 은행 상세 계산 근거 반환
9. 계산 보류와 오류 응답 구현

### 검증 사례

- 모든 조건 충족
- 아무 조건도 충족하지 않음
- 일부 조건 충족
- `모름` 포함
- 복합 조건 보류
- 금액 경계값
- 잘못된 입력

### 완료 조건

- 예상금리가 최고금리를 넘지 않음
- `모름` 조건이 금리에 포함되지 않음
- 수기 계산 5건 이상과 일치
- 같은 요청은 같은 결과를 반환
- SQLite3 테스트가 전부 통과

## 7. Phase 4 — 은행 비교 세로 흐름 완성

**완료(2026-10-29):** 가입 상태·기본 납입액·가입 월·전환 여부·주거래 은행과 우대조건을 입력하고, 14개 은행 결과·차액·상세 근거까지 이어지는 흐름을 완성했다. 브라우저 입력 복원·전체 초기화와 레트로 창 이동·크기 조절도 포함한다.

### 목표

React 사용자가 시작 화면부터 은행 결과와 상세 근거까지 이용할 수 있게 한다.

### 작업

1. 시작 화면 `/`
   - 설문 근거, 서비스 한계, 시작 버튼
2. 조건 입력 `/conditions`
   - 가입 상태, 납입액, 가입 월, 전환 여부, 기존 거래 은행
3. 우대조건 질문
   - `가능·불가능·모름`
4. React 로컬 저장
   - 입력 자동 보관과 복원
   - 전체 초기화
5. 은행 결과 `/banks`
   - 예상금리, 만기액, 조건 상태, 차액
6. 은행 상세 `/banks/[id]`

- 존재하지 않는 경로(404)·허용되지 않는 메서드(405)·예상치 못한 서버 오류(500)를 `{error:{code,message}}` 공통 형식으로 통일했다. 500은 내부 예외 내용을 응답과 로그에 남기지 않고, 허용된 출처에만 CORS 헤더를 붙여 브라우저가 "연결 실패"로 오인하지 않게 했다.

- 2026-10-30, OpenAI Credential 연결을 확인하고 n8n 전체 흐름을 실행했다. Code 노드 4개가 "전체 항목" 모드라 후보 3건 중 첫 건만 OpenAI로 가던 문제를 "항목별 실행" 모드로 고쳤다(저장소 워크플로 JSON과 실행 중인 n8n 모두). 수정 후 3건이 모두 OpenAI→검증→저장을 거쳐 게시됐고 1건은 숫자 검증 거절 뒤 재시도로 통과했다. 토큰 사용량은 입력 451~1033, 출력 219~501이다.

- 2026-10-30, 개발 모델을 `gpt-5.6-luna`로 확정해 적용했다. 요청한 `gpt-5.6-mini`는 이 API 키의 모델 목록에 없었다(5.6 계열은 luna·sol·terra). 이전 기본값 `gpt-6-luna`는 저장소 전체에서 교체했다.
- `gpt-5.6-luna` 표본 평가(금융위 보도자료 서로 다른 7건): 첫 시도 통과 6건, 숫자 검증 거절 1건(재시도에서 통과). 형식·근거 ID 오류와 금지 표현 거절은 없었다. 토큰 합계는 입력 약 7,030, 출력 약 2,450이며 금액은 계산하지 않았다. 근거가 첨부 안내 한 줄뿐인 자료가 2건(88023, 88025)이라 요약 내용이 거의 없다.
- 표본 보충: 금융위 공개 목록 2페이지를 읽기 전용으로 확인해 아직 평가하지 않은 6건을 추가했다. 운영 수집기는 바꾸지 않았다. 평가 전용으로만 같은 공개 목록의 다음 페이지를 읽었다.
- 최종 평가(금융위 보도자료 서로 다른 13건, `gpt-5.6-luna`): 형식·근거 ID 오류와 금지 표현은 0건이다. 첫 시도 통과는 9건(69%)이고 4건은 근거에 없는 숫자(주로 연도)로 거절됐으나 재시도에서 모두 통과해 최종 13건이 게시됐다. 거절은 모두 FastAPI 검증이 잡았다.
- 토큰: 건당 입력 약 450~1,600, 출력 약 220~500이며 13건 합계는 재시도 포함 입력 약 1.8만, 출력 약 0.6만이다. 금액은 모델 가격표를 확인하지 못해 계산하지 않았으므로 OpenAI 사용량 화면에서 확인한다.
- 근거가 첨부파일 안내 한 줄뿐인 자료가 2건(88023, 88025)이라 요약 내용이 거의 없다. Phase 15 화면에서 이런 항목을 어떻게 보일지 정해야 한다.
- 모델은 개발 기본값 `gpt-5.6-luna`로 확정한다. 요청한 `gpt-5.6-mini`는 이 API 키의 모델 목록에 없었다.

## 31. Phase 17 — 납입 감액 영향 설명

### 배경

### 목표

### 작업

- 기준 계획과 변경 계획의 만기액·이자·정부기여금 차이를 FastAPI에서 계산
- 변경한 월 하나를 기준으로 한 달 변경 영향 요약 API
- 감액·미납·원래 납입 유지 3가지 비교 화면
- 계산할 수 없는 중도해지 조건은 임의 추정하지 않고 `추가 확인 필요` 표시
- 납입 유지를 권유하는 표현 없이 차이와 출처만 표시
- 입력 유지, 오류, 360px 화면 처리

### 완료 조건

- 변경 전후 값을 같은 화면에서 확인 가능
- 해지·미납 조건이 불확실하면 추정값을 만들지 않음
- 특정 은행 가입이나 납입 유지를 추천하는 문구가 없음
- 백엔드·프론트 테스트와 빌드 통과
