# Very Rich? 개발 계획

## 0. 목적과 확정 기술

이 문서는 `docs/spec.md`를 React 프론트엔드와 FastAPI 백엔드로 구현하는 순서를 정한다.

| 영역 | 확정 기술 | 역할 |
|---|---|---|
| 프론트엔드 | React + TypeScript | 입력, 화면 이동, 로컬 저장, 결과·오류 표시 |
| 백엔드 | FastAPI | 입력 검증, 기준 데이터 조회, 모든 핵심 금융 계산 |
| 운영 DB | Supabase PostgreSQL | 은행·상품·우대조건·출처·투자 기준 데이터 |
| 개발·테스트 DB | SQLite3 | 로컬 개발, API·계산 자동 테스트 |

계산은 비회원도 사용할 수 있다. 회원가입·로그인은 Supabase Auth를 사용하며, 비회원 답변과 납입액은 브라우저에만 저장한다.

사용자 화면과 문서에는 `Very Rich?`를 사용한다. 폴더명, 패키지명과 배포 주소처럼 물음표를 사용할 수 없는 곳에는 `very-rich`를 사용한다.

---

## 1. 개발 원칙

1. 화면보다 공식 데이터와 계산 정확성을 먼저 확보한다.
2. React는 금융 계산을 복제하지 않고 FastAPI 결과를 표시한다.
3. FastAPI 계산 코드는 Supabase와 SQLite3 중 어느 DB를 사용해도 같은 결과를 내야 한다.
4. 비회원 입력은 DB에 저장하지 않는다. 회원 개인 기록과 별도 동의한 익명 분석 데이터는 서로 분리한다.
5. SQLite3 테스트 통과만으로 운영 호환성을 단정하지 않고 Supabase 연결 검증을 별도로 한다.
6. 은행 비교를 먼저 완성하고 월별 납입, 투자 비교 순으로 확장한다.
7. 계산할 수 없는 조건은 임의 숫자로 만들지 않는다.

## 3. Phase 0 — 개발 기준 확정

### 목표

프로젝트 생성 전에 구조와 저장 원칙을 확정한다.

### 확정 사항

- 프로젝트 루트 아래 `frontend/`, `backend/`로 분리한다.
- 프론트엔드는 React + TypeScript를 사용한다.
- 백엔드는 FastAPI를 사용한다.
- 로컬·자동 테스트 DB는 SQLite3를 사용한다.
- 운영 DB는 Supabase PostgreSQL을 사용한다.
- 비회원 입력은 React의 브라우저 로컬 저장소에만 보관한다.
- FastAPI는 비회원 계산 요청을 영구 저장하지 않는다.
- 회원가입·로그인은 Supabase Auth를 사용하고 자체 비밀번호 DB는 만들지 않는다.
- `처음부터 다시 입력`으로 브라우저 입력을 초기화한다.

### 결정이 남은 내용

- 첫 지원 은행 범위
- 질문을 한 화면에 묶을지 단계별로 보여줄지
- 기존 거래 은행 입력 위치
- 나스닥100·채권의 정확한 비교 기준
- 투자 기간, 환율, 세금과 수수료 처리

투자 관련 결정은 Phase 6 전까지 미뤄도 된다.

### 권장 폴더 구조

```text
very-rich/
├─ frontend/
│  ├─ src/
│  │  ├─ pages/
│  │  ├─ components/
│  │  ├─ features/

│  │  ├─ storage/
│  │  └─ types/
│  └─ tests/
├─ backend/
│  ├─ app/
│  │  ├─ api/
│  │  ├─ models/
│  │  ├─ schemas/
│  │  ├─ repositories/

```

폴더 이름은 역할을 설명하기 위한 기준이며 실제 생성 시 프레임워크 기본 구조에 맞춰 조정할 수 있다.

### 완료 조건

- 기술과 저장 원칙이 PRD·spec·plan에서 서로 일치함
- 사용자 입력과 기준 데이터의 저장 위치가 구분됨
- Phase 1을 시작하는 데 필요한 추가 계정이나 키가 없음

## 4. Phase 1 — React·FastAPI·SQLite3 기반 구축

### 목표

실제 기능 개발 전에 프론트엔드, 백엔드와 테스트 DB가 통신하는 최소 구조를 만든다.

### 1-1. 프론트엔드 생성

- React + TypeScript 프로젝트 생성
- 기본 라우팅 구성
- `/`, `/conditions`, `/banks`, `/banks/[id]`, `/cashflow`, `/alternatives`, `/about` 경로 준비
- 공통 레이아웃과 모바일 기준 폭 준비
- API 요청 모듈 준비
- 브라우저 로컬 저장 모듈 준비

### 1-2. 백엔드 생성

- FastAPI 프로젝트 생성
- API 버전 경로 구성
- 요청·응답 스키마 구조 준비
- 서비스, 계산기, 저장소 계층 분리
- 공통 오류 응답 형식 준비
- 허용된 프론트엔드 주소에서만 개발 요청을 받을 수 있게 설정

### 1-3. SQLite3 연결

- 로컬 개발용 SQLite3 연결 설정
- 기준 데이터용 초기 테이블 준비
- 테스트마다 독립 DB를 만들고 초기화할 수 있게 구성
- 운영 DB에 종속된 PostgreSQL 전용 기능은 아직 사용하지 않음

### 1-4. 최소 연결 확인

- FastAPI 상태 확인 API 준비
- React가 상태 확인 API를 호출해 정상 응답을 표시
- 백엔드가 SQLite3에 연결해 기준 데이터 한 건을 읽는지 확인
- 사용자 입력이 DB에 저장되지 않는지 확인

### 1-5. 테스트 기반

- 백엔드 단위 테스트
- FastAPI 요청·응답 테스트
- SQLite3 저장소 테스트
- React 기본 화면·입력 테스트
- 프론트엔드와 백엔드 실행 방법 문서화

### 산출물

- 실행 가능한 React 앱
- 실행 가능한 FastAPI 앱
- SQLite3 개발·테스트 설정
- 최소 API 통신
- 기본 테스트 명령
- 환경변수 예시 파일

### 완료 조건

- 프론트엔드와 백엔드를 각각 실행할 수 있음
- React에서 FastAPI 정상 응답을 확인할 수 있음
- 자동 테스트가 SQLite3로 실행됨
- 비밀값이 저장소에 포함되지 않음
- 금융 기능은 아직 임시 숫자로 구현하지 않음

## 5. Phase 2 — 공식 상품 데이터 구축

**완료(2026-10-28):** SQLite3에 공통 정책, KB국민은행·신한은행 상품, 우대조건과 공식 출처를 구축했다. Supabase 연결은 Phase 8로 유지한다.

### 목표

청년미래적금 계산에 필요한 공통 규칙과 은행별 공시를 DB 구조로 정리한다.

### 작업

1. 공통 상품 규칙 정리
   - 가입 기간과 납입 범위
   - 정부기여금과 세금 규칙
   - 전환 가입 관련 규칙
2. 첫 지원 은행 범위 확정
3. 은행별 정보 정리
   - 은행·상품명
   - 기본·최고금리
   - 우대조건과 가산금리
   - 조건 결합 방식
   - 공시 URL과 기준일
4. 사용자 질문, 계산 조건, 쉬운 설명을 분리
5. 자동 계산 불가능 조건을 `추가 확인 필요`로 구분
6. SQLite3 초기 데이터 작성
7. 공식 원문과 사람 검수

### DB 원칙

- Supabase와 SQLite3에서 사용할 핵심 필드명을 같게 유지한다.
- 사용자 답변이나 계산 결과 테이블은 만들지 않는다.
- 금액과 금리는 부동소수점 오차를 피할 수 있는 형식으로 다룬다.
- 모든 공시 데이터에 기준일과 출처를 둔다.

### 완료 조건

- 지원 은행 데이터가 빠짐없이 SQLite3에 들어 있음
- 모든 금리와 조건에 공식 근거가 있음
- 최고금리와 조건별 금리 합계가 검수됨
- 자동 계산 보류 조건이 분리됨

## 6. Phase 3 — 적금 계산 API 완성

**완료(2026-10-28):** 상품·질문 조회 API와 고정 월 납입 계산 API를 구현했다. `모름`과 추가 증빙 조건은 금리에서 제외하며 17개 백엔드 테스트를 통과했다.

### 목표

FastAPI가 사용자 입력과 SQLite3 기준 데이터를 이용해 적금 결과와 근거를 반환하게 한다.

### 작업

1. 기본 계획 요청 검증
2. 우대조건 상태 계산
   - 반영됨
   - 반영되지 않음
   - 추가 확인 필요
3. 예상금리 계산
4. 월 기본 납입 기준 이자 계산
5. 정부기여금 계산
6. 예상 만기 수령액 계산
7. 은행별 결과 정렬용 값 반환
8. 은행 상세 계산 근거 반환
9. 계산 보류와 오류 응답 구현

### 검증 사례

- 모든 조건 충족
- 아무 조건도 충족하지 않음
- 일부 조건 충족
- `모름` 포함
- 복합 조건 보류
- 금액 경계값
- 잘못된 입력

### 완료 조건

- 예상금리가 최고금리를 넘지 않음
- `모름` 조건이 금리에 포함되지 않음
- 수기 계산 5건 이상과 일치
- 같은 요청은 같은 결과를 반환
- SQLite3 테스트가 전부 통과

## 7. Phase 4 — 은행 비교 세로 흐름 완성

### 목표

React 사용자가 시작 화면부터 은행 결과와 상세 근거까지 이용할 수 있게 한다.

### 작업

1. 시작 화면 `/`
   - 설문 근거, 서비스 한계, 시작 버튼
2. 조건 입력 `/conditions`
   - 가입 상태, 납입액, 가입 월, 전환 여부, 기존 거래 은행
3. 우대조건 질문
   - `가능·불가능·모름`
4. React 로컬 저장
   - 입력 자동 보관과 복원
   - 전체 초기화
5. 은행 결과 `/banks`
   - 예상금리, 만기액, 조건 상태, 차액
6. 은행 상세 `/banks/[id]`
   - 계산식, 쉬운 설명, 공시 원문
7. FastAPI 오류와 입력 오류 표시

### 완료 조건

- 시작→조건→결과→상세 흐름이 끊기지 않음
- 새로고침 후 입력값이 복원됨
- 초기화 후 브라우저 입력이 삭제됨
- 사용자 입력이 SQLite3에 저장되지 않음
- React에 금융 계산식이 중복 구현되지 않음

## 8. Phase 5 — 월별 납입 기능

### 목표

감액과 미납을 포함한 실제·계획 현금흐름을 FastAPI 계산에 적용한다.

### 작업

- 월별 납입 입력 화면 `/cashflow`
- 기본 납입액으로 전체 월 초기화
- 월별 수정과 0원 입력
- 과거 실제값과 미래 계획 구분
- FastAPI 월별 현금흐름 검증
- 총 원금, 이자, 기여금, 만기액 재계산
- 고정 납입 결과와 차이 표시

### 검증 사례

- 매월 동일 금액
- 한 달 감액
- 한 달 미납
- 여러 달 감액·미납
- 과거 실제값과 미래 계획 혼합

### 완료 조건

- 월별 합계와 총 원금이 일치
- 0원인 달에 기여금이 포함되지 않음
- 수정 결과가 FastAPI 계산에 반영됨
- 사용자 월별 입력이 DB에 저장되지 않음

---

## 9. Phase 6 — 투자 데이터와 계산

### 목표

동일한 월별 현금흐름을 적용할 수 있도록 투자 대상별 기준과 계산기를 완성한다.

### 결정·구축 대상

- 나스닥100: QQQ 사용 여부 최종 확정
- SCHD: 배당 재투자와 세금 처리
- QLD: 실제 시계열 사용, 레버리지 위험
- 채권: 대표 채권 ETF와 만기 범위
- 다른 예·적금: 비교 금리 기준
- 거래일이 아닌 납입일 처리
- USD/KRW 환율 적용
- 세금과 수수료 적용

### 백엔드 작업

- 투자 기준 데이터 저장 구조
- 자산별 시계열 조회 구조
- 동일 날짜·금액 적용 계산기
- 평가금액, 수익·손실, 변동 정보
- 자료 누락과 계산 보류 응답
- QLD를 단순 2배로 계산하지 않는 테스트

### 완료 조건

- 각 자산에 출처와 기준일이 있음
- 상승·하락 구간 표본 계산이 검증됨
- 같은 현금흐름을 모든 자산에 적용 가능
- QLD가 실제 시계열로 계산됨

---

## 10. Phase 7 — 적금·투자 비교

### 목표

React에서 동일한 현금흐름의 적금과 대안 결과를 비교한다.

### 작업

- 비교 대상 선택 UI
- FastAPI 비교 요청
- 원금, 종료 결과, 수익·손실 표시
- 기간과 출처 표시
- 배당·환율·세금·수수료 반영 여부 표시
- 원금 손실과 QLD 레버리지 경고
- 일부 자산 실패 시 해당 자산만 보류
- 추천·수익 보장 표현 검수

### 완료 조건

- 동일 날짜와 금액 적용이 확인됨
- 위험과 결과가 함께 표시됨
- 미반영 요소가 숨겨지지 않음
- 계산은 FastAPI 한 곳에서 수행됨

## 11. Phase 8 — Supabase 운영 연결

**연결 준비(2026-10-28):** psycopg 드라이버, Session pooler 환경변수, Alembic 초기 마이그레이션을 구성했다. 실제 Supabase 연결과 `upgrade head` 적용은 연결 정보 입력 후 확인한다.

### 목표

SQLite3에서 검증한 기준 데이터 구조를 Supabase PostgreSQL에 적용하고 운영 조회를 확인한다.

### 작업

- Supabase 프로젝트 준비
- 운영 DB 연결 문자열을 로컬 비밀 환경변수로 설정
- 스키마 마이그레이션
- 은행·상품·조건·출처 데이터 적재
- 필요 시 투자 기준 데이터 적재
- FastAPI 운영 DB 연결 설정
- SQLite3와 Supabase 조회 결과의 핵심 필드 비교
- 개인 기록과 동의 기반 익명 분석 테이블이 분리되어 있는지 확인
- 비밀키가 프론트엔드와 저장소에 노출되지 않는지 확인

### 주의

- Supabase 서비스 키와 DB 비밀번호는 FastAPI 실행 환경에만 둔다.
- React에 DB 비밀번호나 서비스 키를 넣지 않는다.
- Supabase Auth 이메일 인증 설정과 리디렉션 주소를 검증한다.
- PostgreSQL과 SQLite3의 날짜·숫자·정렬 차이를 검증한다.

### 완료 조건

- FastAPI가 Supabase 기준 데이터를 읽음
- SQLite3 테스트는 계속 통과함
- 운영·테스트 환경 전환이 설정값으로 구분됨
- 비밀값이 코드에 포함되지 않음

## 12. Phase 9 — 출처·오류·통합 QA

### 목표

모든 숫자의 근거를 보여주고 전체 흐름과 모바일 사용성을 검증한다.

### 작업

- `/about` 계산 기준 화면
- 설문, 상품 공시, 투자 데이터 출처 표시
- 입력 오류, 데이터 없음, 계산 보류, 네트워크 실패 처리

- 360px 모바일 검증
- 계산 회귀 테스트
- Supabase 연결 통합 테스트
- 제외 기능이 추가되지 않았는지 확인

### 완료 조건

- `spec.md` 완료 확인표 통과
- 심각한 계산 오류 없음
- 출처·기준일·미반영 요소 확인 가능
- 실패 결과가 정상 숫자로 보이지 않음
- 모바일에서 전체 흐름 사용 가능

## 15. 중단 기준

다음 문제가 있으면 다음 Phase로 넘어가지 않는다.

- 공식 출처 없는 금리나 조건
- 수기 계산과 맞지 않는 적금 결과
- React와 FastAPI가 서로 다른 계산 수행
- 비회원 입력 또는 동의하지 않은 분석 데이터가 DB에 저장됨
- SQLite3 테스트 실패
- Supabase와 SQLite3 핵심 필드 불일치
- QLD 단순 2배 계산
- 투자 결과가 추천·예측처럼 표시됨
- 출처와 기준일 누락
- 비밀키가 프론트엔드 또는 코드에 포함됨

## 16. 사용자 준비가 필요한 시점

### Phase 0~7

사용자가 별도로 제공해야 할 값은 없다. 로컬 React·FastAPI·SQLite3 환경으로 진행할 수 있다.

### Phase 8 시작 전

사용자가 준비해야 한다.

- Supabase 프로젝트
- PostgreSQL 연결 문자열 또는 필요한 연결 정보
- 운영 환경에서 사용할 비밀값 설정 위치

비밀번호와 키는 채팅으로 전달하지 않고 프로젝트의 로컬 환경변수 또는 배포 환경의 비밀 설정에 직접 입력한다.

### 공개 전

배포 위치는 아직 정하지 않았다. 프론트엔드와 FastAPI 배포 서비스가 결정되면 해당 계정 또는 환경 설정이 필요하다.
